# Асаны: истоки

Статический сайт для изучения того, как асаны описаны в первоисточниках.
Слева — список асан трактата, справа — текст этого трактата об асане:
деванагари, IAST, кириллическая транслитерация, пословный разбор, буквальный
и литературный перевод, примечания к чтениям.

В собрании семь памятников:

* **Ахирбудхнья-самхита, XXXI глава** — одиннадцать главных асан;
* **Васишт̣ха-сам̣хитā, Йога-кāн̣д̣а, гл. 1, ст. 67–82** — десять асан, каждая
  разобрана по стихам;
* **Ма̄насолла̄са, улласа IX, ст. 24–26** — пятнадцать асан, названных в трёх
  стихах и разнесённых по божествам;
* **Хат̣хататтвакаумудӣ, гл. 7, шлоки 1–45** — пятнадцать асан с бандхами;
* **Ш́āрн̇гадхара-паддхати, гл. 157–158, ст. 4375–4437** — три асаны антологии
  1363 г.;
* **Даттāтрея-йога-ш́āстра** (критическое издание Дж. Маллинсона, 2024) — три
  асаны: Падмāсана (ст. 34–38), Ш́авāсана (ст. 24cd–26), Випарӣта-каран̣ӣ
  (ст. 146–149);
* **Хат̣хапрадӣпикā, гл. 1, ст. 1.19–1.54** (критическое электронное издание
  «Light on Haṭha Yoga», Оксфорд – Марбург, 2024) — все пятнадцать асан
  Свāтмāрāмы, от свастики до бхадра/горакша, с рамкой главы: вступление
  (1.17–1.18), «четыре главные асаны и 84 позы» (1.33–1.34) и переход
  к прāн̣āйāме (1.55–1.56).

Трактат выбирается в списке слева сверху. Асаны всех памятников совпадают по
ключам, поэтому страница асаны показывает описания из всех, где она названа,
подряд, каждое — со своей датировкой. Асана, которой нет в выбранном трактате,
в списке приглушена.

Тексты приведены дословно по источникам, без добавлений и реконструкций.

Если текст одного трактата ссылается на «Хат̣хапрадӣпику» («ср. HP 1.30»,
«HP 3.79–82»), рядом с этим местом встаёт справка: сам стих — деванагари,
IAST, кириллица, перевод издания, метр — и весь аппарат с полными названиями
рукописей. Ни листать, ни переключать трактат, ни догадываться, о каком стихе
речь, не нужно. Сокращения, которыми источники печатают аппарат (GOML, NGMPP,
BISM, MSPP, DAV …), расшифрованы в начале того же раздела — в
`data/abbreviations.json`; в цитатах сокращение остаётся как напечатано.

Глава 3 «Хат̣хапрадӣпики» добавлена отдельным файлом: в двух PDF была только
глава 1, а Випарӣта-каран̣ӣ описана в главе 3 (стихи 3.73–3.77 критического
издания; в изданиях старой нумерации — 3.79–3.82, так их и цитирует издание
Даттāтрея-йоги).

## Адреса страниц и сборка

Каждая асана и каждый трактат — отдельный адрес, а не хеш в одном документе:
`/asana/padmasana/`, `/treatise/manasollasa/`,
`/treatise/manasollasa/introduction/`, и то же самое под `/en/`. Общие части
адреса — латинские слова, а не транслит: `asana`, `treatise`, `introduction`.
Адрес страницы не зависит от языка: русская и английская версии различаются
только префиксом `/en/`, поэтому в генераторе нет таблицы перевода сегментов.
Это важно не для красоты: по хеш-адресу поисковик видит один документ, а
ассистенты (ChatGPT, Claude, Perplexity) вообще не исполняют JavaScript — им
нужен текст в самом HTML.

Страницы пишет `tools/prerender.js`: он открывает `index.html`, загружает
`assets/app.js` в jsdom и ждёт, пока приложение отрисует маршрут, а затем
сохраняет получившийся документ в `asana/<key>/index.html` и соседние. Второго
рендера нет — разметка статической страницы это ровно та разметка, которую
строит браузер, поэтому они не могут разойтись. Скрипт остаётся на странице:
вкладки письма, тема, фильтр по списку асан и переходы стрелками работают как
раньше.

Что попадает в `<head>` каждой страницы: свой `<title>`, описание, собранное
из её же заголовка и глоссы, `canonical`, пара `hreflang` ru/en (и `x-default`
на русскую версию), Open Graph и микроразметка `WebPage` + `BreadcrumbList`.
`robots.txt` и `sitemap.xml` собираются из того же списка страниц, поэтому
страница не может быть в одном и отсутствовать в другом.

```bash
npm install                 # один раз: jsdom
node tools/prerender.js     # собрать страницы, sitemap.xml, robots.txt
node tools/prerender.js --check   # только сказать, отстали ли страницы от данных
cd tools && python3 prerender_check.py   # проверить собранное
```

`--check` сравнивает файлы с тем, что отрисовал бы сайт сейчас, — его стоит
запускать после правок в `data/` или `assets/app.js`. `prerender_check.py`
ловит и то, что `--check` пропустит по определению, потому что это совпадёт
с данными: пустые абзацы (признак блока, которого не понял рендер) и
пословный разбор, разложенный по одной букве. Идентификаторы вкладок
считаются, а не берутся случайными (`verseSeq`), иначе страницы различались бы
при каждой сборке и проверка была бы бесполезной.

Свой домен пока не заведён: адрес сайта записан одной строкой — `SITE` в
`tools/prerender.js`. При переезде меняется она и `CNAME`, дальше всё (canonical,
hreflang, sitemap) пересобирается само.

### Как добавить трактат

1. Положить PDF в `sources/` и написать сборщик JSON (как `tools/extract_*.py`);
2. дописать трактат в `data/treatises.json`;
3. `node tools/prerender.js` — страницы нового трактата и его асан появятся
   сами, вместе с адресами, описаниями и строками в sitemap. Руками ничего
   перечислять не нужно: маршруты берутся из данных.

## Локальный просмотр

Открывать `index.html` двойным щелчком нельзя: браузер не отдаст JSON через
`file://`. Нужен любой статический сервер:

```bash
python3 -m http.server 8080
# затем http://localhost:8080
#       http://localhost:8080/asana/padmasana/
```

## Как данные получаются из PDF

`data/ahirbudhnya-samhita.json` не набирался руками. Скрипт читает PDF из
`sources/`, разбирает его на структурные блоки (стихи, пословный разбор,
переводы, примечания) и складывает в JSON. Формулировки при этом копируются
символами исходника.

```bash
pip install pymupdf
cd tools
python3 extract.py ../data/ahirbudhnya-samhita.json
python3 extract_vasishtha.py ../data/vasishtha-samhita.json
```

Второй скрипт устроен сложнее: в PDF Васишт̣ха-сам̣хиты есть заголовки двух
уровней, вложенные списки, таблица датировок, английские цитаты с русским
переводом и разрывы абзацев через границу страницы. Он собирает всё это в
блоки (`h2`, `h3`, `h4`, `p`, `list`, `quote`, `table`), не меняя текст.

Пословный разбор в русском издании Ахирбудхнйа-сам̣хиты напечатан латиницей
(IAST), поэтому скрипт переписывает термины кириллицей по одной карте
(`tools/translit.py`) — с точкой **под** «м»: `ṃ`/`ṁ` → `м̣`, `ṛ` → `р̣`,
`ṝ` → `р̣̄`, `ḷ` → `л̣`, `ś` → `ш́`, `ṣ` → `ш`, `ṇ` → `н̣`, `ṭ` → `т̣`,
`ḍ` → `д̣`, `ñ` → `н̃`, `ṅ` → `н̇`, `ḥ` → `х̣`, `ā` остаётся латинской.
В английской версии термины остаются латиницей с диакритикой, как в PDF.
Строки «кириллической транслитерации» стихов из более старого PDF (там точка
стояла над «м») приводятся к той же карте — меняется только знак над буквой,
сами строки и разбивка на строки не трогаются.
Проверить соответствие схемы можно так:

```bash
cd tools && python3 translit.py
# verse lines reproduced from the printed transliteration: 23 / 28
```

Расхождения в пяти строках — это места, где сама печатная транслитерация
отличается от строки IAST (другое чтение, редакторские скобки), а не ошибки
таблицы.

В конце работы скрипт печатает проверку: какие строки PDF не попали в JSON.
Сейчас в отчёте остаются только заголовки разделов — они хранятся в данных
отдельно (как названия асан, номера стихов и подзаголовки), а не как текст
абзацев.

## Знаки у каждого санскритского слова

Печатные издания ставят знаки непоследовательно: в одном месте «āсана», в другом
«асана», а в колонтитулах Ахирбудхнйа-сам̣хиты названия асан напечатаны вовсе без
знаков («Майурасана»). Сайт показывает одно написание: у санскритского слова
стоят те знаки, которые нужны по карте транслитерации. Скрипт `tools/sanskrit.py`
делает это для русских подписей, названий асан, перечней, пословного разбора и
прозаических разделов; английская версия и строки стихов не трогаются — там
текст уже напечатан с диакритикой.

Скрипт только добавляет знаки: ни одна буква не вставляется, не убирается и не
переставляется. Общие подписи сайта («Āсаны», «Найти āсану», «Пāн̃чарāтра»)
правятся вручную в `index.html`, `assets/app.js` и `data/treatises.json`.
Проверка — тем же скриптом, он печатает список мест, где знаки ещё не стоят:

```bash
cd tools && python3 sanskrit.py
# strings that would change: 0
```

## Имена исследователей

Краткая датировка под названием асаны показывает все даты статьи, а не один
лагерь: пока в ней стояли только строки таблицы §2.4, пять авторов «ок. 700»
читались как весь список литературы о вопросе.

Краткие строки датировки — это собственный конспект сайта:
кто предлагает дату и на чём основывается. В русском томе Ахирбудхнйа-сам̣хиты
имена уже стоят по-русски («Ф. Отто Шрадер», «Д. Вьюстик», «Марион Растелли»),
а таблица в томе Васишт̣ха-сам̣хиты называет работы по латинским ключам
библиографии. Чтобы одна и та же колонка не читалась двумя способами,
`tools/authors.py` даёт русское написание фамилий — ровно в том виде, в каком
эти фамилии пишет русский текст тех же изданий («Бёрч», «Буи», «Маллинсон и
Синглтон», «Вьюстик», «Кола́» — с ударением, как в издании).

Меняются только фамилии. Годы, названия работ, цитаты («as shown below»,
«Chronology») и подписи разделов остаются как напечатано, потому что это
цитаты. Полная статья о датировке — дословная, её скрипт не трогает.

```bash
cd tools && python3 authors.py
# strings that would change: 0
```

## Диакритика в кириллице

Знаков «м с точкой снизу» и подобных в большинстве шрифтов нет, поэтому браузер
подставлял для таких букв другой шрифт: буква выглядела жирнее соседних, а
межбуквенный интервал (`letter-spacing`) сдвигал точку в сторону. Поэтому знак
рисуется средствами CSS (`.mk` в `assets/style.css`) прямо над/под буквой, а
настоящий комбинируемый символ остаётся в тексте с нулевым кеглем — благодаря
этому копирование, поиск по странице и скринридеры получают правильную букву.

Знак отсчитывается **от базовой линии**, а не от низа строки: `.mk` —
`inline-block` высотой `1em` с `line-height: 1`, поэтому низ его бокса стоит
ниже базовой линии на постоянную величину шрифта, а не на высоту строки. Раньше
отсчёт шёл от низа строки, и в тексте с `line-height: 1.7` (это основной текст
сайта) черта долготы ложилась поперёк буквы: «а̄» выглядела как перечёркнутая
«а». Расстояние до знака задано в `ex` — в высоте строчной буквы, — потому что у
Cormorant Garamond она меньше, чем у Spectral. У прописных (`is-cap`) знак идёт
над верхом заглавной буквы.

### Знаки в самом шрифте

В Spectral и Cormorant Garamond у кириллицы нет якорей GPOS mark-to-base: знак
(точка, акут, макрон) не прикрепляется к букве, а рисуется **справа от неё** —
то есть поверх следующей буквы. Именно это и выглядит как «буквы наползли друг
на друга». В обычном тексте это лечит `.mk` с CSS-знаками, но там, где разметку
поставить нельзя — в `<option>` выпадающего списка трактатов, в `title`
страницы, в скопированном тексте, — знак оставался поверх соседней буквы.

Поэтому `tools/build_fonts.py` дописывает якоря в сами шрифты
(`add_cyrillic_mark_anchors`): mark-to-base для всех кириллических букв и пяти
знаков (`U+0323`, `U+0307`, `U+0304`, `U+0301`, `U+0303`). После этого знак
встаёт над своей буквой в любом контексте, а `.mk` продолжает работать как
раньше (внутри `.mk` настоящий знак скрыт — `font-size: 0` — поэтому знак не
рисуется дважды).

Три вещи, без которых якоря не работают (все три стоили отладки):

- покрытие (Coverage) в GPOS должно быть **отсортировано по номеру глифа**,
  иначе HarfBuzz не находит таблицу;
- новую запись в `FeatureList` дописывать нельзя: по спецификации она
  сортируется по тегу, а поиск идёт двоичный — дописанная в конец запись не
  находится. Наш lookup добавляется к уже существующей фиче `mark`;
- буквам нужен класс 1 в GDEF (обычные глифы, а не mark), иначе якоря
  игнорируются.

Проверка: `python3 tools/build_fonts.py --marks-only` (дописывает якоря в готовые
файлы) или обычная сборка. Результат виден по сдвигу знака:

```bash
# до:  м + U+0323 → x_offset 0, y_offset 0  (точка справа от буквы, adv 0)
# после: м + U+0323 → x_offset −353, y_offset −38 (по центру буквы, под ней)
```

Версия шрифтов стоит в адресе (`font-face` → `?v=`), та же, что у `style.css` в
`index.html`: иначе браузер держит старый файл из кеша.

Внутри `.mk` межбуквенный интервал (`letter-spacing`) погашен: он наследуется
внутрь бокса, где стоит одна буква, и добавляет ширину справа — а знак стоит по
центру бокса, поэтому съезжал бы вправо на половину интервала. Снаружи интервал
добавляет родитель, ровно один раз.

Все точки снизу стоят на одной высоте: `м̣`, `н̣`, `т̣`, `х̣`, `д̣`, `л̣`, `ш̣`,
`к̣`, `с̣` — одна и та же линия в любом начертании и кегле. Исключение одно:
у «р» хвост уходит вниз ровно под точкой, поэтому `р̣` опускается под хвост.
У «д» ножки стоят по краям, а под точкой в середине буквы пусто — раньше её
точка тоже опускалась (по ошибке, «на всякий случай») и выглядела ниже, чем у
«н»; теперь она на общей линии.

Перенос длинных слов задан `overflow-wrap: break-word` — на всём сайте, а на
ссылках `anywhere`. Разница важна: `break-word` срабатывает только там, где
слово не влезает в свою колонку целиком, и обычные слова не рвёт; `anywhere`
меняет расчёт ширины (min-content) и может сжать таблицу в столбик по букве.
Колонка терминов в пословном разборе — `minmax(120px, 31%)`; самый длинный
термин занимает 11.8em, и в узком окне без `break-word` его буквы уезжали
поверх колонки перевода.

## Шрифты

Шрифты лежат в `assets/fonts` (`Spectral`, `Cormorant Garamond`,
`Noto Serif Devanagari`), по одному файлу woff2 на начертание, лицензия OFL —
рядом, в тех же каталогах. Сборка:

```bash
npm i @expo-google-fonts/spectral @expo-google-fonts/cormorant-garamond \
      @fontsource/noto-serif-devanagari
python3 tools/build_fonts.py --src node_modules
```

Свои файлы нужны не ради скорости, а ради диакритики. Google Fonts отдаёт шрифт
нарезанным по `unicode-range`: кириллическая «а» лежит в кириллическом наборе, а
знак долготы `U+0304` — только в latin-ext. Браузер берёт букву из одного файла,
знак из другого, склеить их по GPOS уже нельзя, и знак садится не над буквой.
Кроме того, в Spectral и Cormorant Garamond у части кириллических букв (м, н, ш,
р, т, д, в, х) нет якорей mark-to-base, поэтому знаки всё равно рисует CSS.
Сборка берёт полные файлы и режет их сама, сохраняя таблицы GPOS
(`--layout-features=*`).

## Кеш GitHub Pages

Pages отдаёт файлы с `Cache-Control: max-age=600`, поэтому браузер может
показывать старые `app.js` и JSON. От этого стоят параметры версии: `?v=` у
`assets/style.css` и `assets/app.js` в `index.html` и константа `BUILD` в
`assets/app.js` (ею помечаются запросы к данным). После правок увеличьте обе —
читатель сразу получит новую версию, а текущая сборка видна в подписи под
страницей асаны («версия …»).

## Датировка

Страница асаны идёт сплошным текстом: название асаны, затем — по каждому
трактату — название источника с номером главы, сразу под ним краткая датировка
(век или год, кто датирует и работа, на которую опирается дата), дальше сам
текст. Ничего не спрятано в раскрывающиеся блоки, кроме самой статьи о
датировке. Кнопка «Читать датировку
полностью» раскрывает весь раздел о датировке — дословно, как в источнике.
Краткие строки лежат в `data/treatises.json` (`datingSummary`), полный текст —
в `data/<трактат>.json` в поле `dating` (собирается из PDF автоматически), и он
же остаётся в статье на странице «О трактате».

## Номера глав — арабскими цифрами

Источники нумеруют главы то римскими, то арабскими цифрами: в одном трактате
«XXXI глава», в другом «глава 1», в третьем «улласа IX», а в английском томе
«chapter XXXI». Сайт везде показывает одно и то же — арабские цифры.

Этим занят `tools/numeral.py`: все три сборщика вызывают его на готовом JSON
(`numeral.fix_document(data)`), поэтому в `data/*.json` римских номеров глав уже
нет, а поле `chapter` записано как `"31"`, `"1"`, `"9"`.

Правило узкое, чтобы не пострадал ни один другой номер:

* меняется только то число, которое стоит рядом со словом «глава» (`глава
  XXXI`, `XXXI глава`, `гл. I`, `chapter XXXI`, `ch. I`, `ullāsa IX`,
  `улласа IX`), и ссылка вида «глава.стих» (`IX.24` → `9.24`);
* века (`XII–XIII века`), тома (`т. II`), шифры и каталожные номера (`Oudh
  VIII, 24`), перечни в тексте (`I. Текст…`, `II. Комментарий…`) остаются как
  напечатано: это не номера глав;
* ссылка «глава.стих» переводится и тогда, когда её глава совпадает по числу с
  главой трактата (`I.33` Йога-сӯтры в томе Васишт̣ха-сам̣хиты); меняется только
  запись числа, само число и его смысл — нет;
* значение числа не меняется никогда: XXXI — это 31 и остаётся 31, ни одно
  слово не добавлено, не убрано и не переставлено.

Проверка: `python3 tools/numeral.py` печатает контрольные строки до и после;
`python3 tools/numeral.py data/*.json` конвертирует уже собранные файлы (после
этого изменений быть не должно — иначе пересоберите JSON).

## Как добавить третий трактат

1. Положить PDF (или транслитерацию) в `sources/`.
2. Собрать по той же схеме JSON: `poses[]` с полями
   `key`, `iast`, `number`, `name{ru,en}`, `gloss{ru,en}`, `verses{ru,en}`,
   `text{ru:[…], en:[…]}`; блоки текста бывают типов `verse_card`
   (`verses`, `sections[]` из `verse` с `lines`), `verse` (`lines`),
   `words` (`groups` — список разборов по стихам, каждый — пары
   `[термин, значение]`; разбор одного стиха — одна группа, то есть
   `groups: [[["uttānau","turned soles upward"], …]]` — именно на один уровень
   вложенности глубже, чем пары; на всякий случай `assets/app.js` принимает и
   плоский список пар, но в данных держим одну форму), `prose` / `note` (`paragraphs`), `subhead`,
   `p` (`text`), `h3` / `h4` (`text`) — заголовок или абзац внутри раздела.
   Блоки статьи о трактате и раздела о датировке — это `title`, `h2`, `h3`,
   `h4`, `p`, `list` (`items` — строки или `{html, level}`), `quote`
   (`paragraphs`), `table` (`rows`). Поле `html` содержит разметку курсива и
   жирного, взятую из PDF.
   Ключ `key` общий для всех трактатов: именно по нему асана одной школы
   сопоставляется с асаной другой. Если в трактате есть асана, которой нет в
   списке, просто добавьте её `key` — она появится в списке этого трактата.
3. Добавить запись в `data/treatises.json` (id, file, название, традиция,
   издание, переводчик, ссылка на PDF, при наличии — `datingSummary` с полями
   `note`, `label` (подпись последнего столбца) и `items[]` (`who`, `when`,
   `whenNote`, `work`)). Если `datingSummary` записан в самом JSON трактата, он
   имеет приоритет над записью в индексе — так краткая датировка собирается из
   таблицы PDF без ручного набора.

Когда одна и та же асана есть в нескольких трактатах, её страница показывает
описания по каждому трактату подряд, с заголовком источника.

## Третий трактат: «Ма̄насолла̄са»

`tools/extract_manasollasa.py` собирает `data/manasollasa.json` из двух PDF
(русского и английского). Устроен он иначе, чем первые два:

* асаны здесь не описаны, а только названы в стихах 24–26 девятой уллы, и
  страница позы собрана в том же порядке, что и в первых двух трактатах:
  **стихи** (девана̄гарӣ, IAST, кириллица — по одному блоку на строку стиха,
  с номером стиха над карточкой), **пословный разбор**, **буквальный
  перевод**, **литературный перевод**, затем **классификация по божествам**
  из §6.3 с цитатой девана̄гарӣ;
* стихи на странице позы цитируются целиком — все три (24, 25, 26), а не та
  строка, в которой стоит выбранная асана: одна строка из четырнадцати
  названий ничего не говорит о том, что это за классификация. Вместе с ними
  целиком идут и пословный разбор (по стиху на столбец, с подписью «Стих 24»
  и т. д.), и оба перевода; своей у асаны остаётся только её собственная
  строка §6.3. Стих, в котором названа открытая асана, помечен над карточкой
  («здесь названа эта асана»), чтобы на пятнадцати похожих страницах было
  видно, какой из трёх стихов её и называет. Номера стихов `verse_groups()`
  берёт из самого издания (там число стоит в конце стиха — `॥२५॥`), а
  `pose_text()` проверяет, что асана действительно названа в том стихе,
  который стоит у неё в ссылке;
* пословного разбора в самой справке нет, поэтому он собран из её же слов:
  в `WORDS` каждое слово стиха (разделённое так, как это делает сама справка
  в §6.5) получает ровно тот перевод, который стоит на его месте в переводе
  §6.2; `check_words()` не даёт собрать страницы, если слово не совпало с
  текстом стиха или перевода — то есть ничего не дописано;
* «буквальный перевод» — перевод самой справки (§6.2), «литературный» —
  перевод изд. 1978 г., приведённый в справке дословно, с указанием
  страницы под ним;
* весь остальной текст справки (§0–§5, §6.1, §6.4–§10) лежит в поле `about`,
  §2 (датировка) — в поле `dating`; краткие строки датировки под названием
  асаны (`datingSummary.groups`) идут тремя группами, как сама статья делит
  даты: лагерь §2.3 («Ш́ан̇кара 788–820»), лагерь §2.4 («ок. 700») и
  традиционные даты §2.2. Две группы — это таблицы источника, взятые как
  есть; строки §2.3 переписаны из её прозы и списка, и `check_dating_rows()`
  не даёт собрать данные, если хоть одна такая строка не найдена в тексте
  статьи дословно;
* в блоках появились два новых типа: `deva` (`lines` — строки девана̄гарӣ) и
  `code` (`text` — пример из §8); нумерованный список — это `list` с
  `ordered: true` и `start`, вложенный в пункт пример кода — поле `code`
  у пункта.

Девана̄гарӣ в этих PDF набрана шрифтом с испорченной таблицей символов: часть
глифов на границах фрагментов выходит латиницей или служебными знаками
(`स्वस्ति\x0f\x10कं`, `वार्त्तिÚKक`). `clean_runs()` убирает только такие
посторонние знаки — ни одна буква девана̄гарӣ не сдвигается и не удаляется.
Скрипт печатает всё, что убрал, вместе с контекстом, чтобы это можно было
сверить построчно.

## Пятый трактат: «Ш́āрн̇гадхара-паддхати»

`tools/extract_sharngadhara.py` собирает `data/sharngadharapaddhati.json` из двух
PDF — русского (14 страниц) и английского (11). Оба тома построены одинаково и
повторяют схему статьи, а не книги: часть I — датировка (колофоны, стихи 1.2–1.6,
синхронизм с Хаммӣрадевой, границы и история изучения), часть II — корпус: девять
стихов об āсанах из глав 157–158, часть III — сравнительная таблица и вывод.

* разметка в этих PDF подделана шрифтами: заголовки и курсив набраны
  псевдошрифтами `Type3` того же 12 pt, что и основной текст, поэтому по размеру
  кегля заголовок не отличить от абзаца. Заголовком считается либо строка
  `Тип 5` в 14/16 pt, либо полностью полужирная строка 12 pt с отступа 72 pt.
  Настоящих заголовков стихов (полужирных) нет — они набраны обычным `ArialMT`,
  и `VERSE_HEAD` узнаёт их по образцу `1. Стих 4375: …` / `1. Verse 4375: …`,
  независимо от начертания. Полужирная строка внутри абзаца узнаётся по
  строчной первой букве и остаётся текстом (в русском томе так набрана одна
  фраза вступительного абзаца части I);
* асана уходит на свою страницу только там, где она названа в заголовке стиха:
  таких стихов три (Падмāсана — 4376, 4377 и повтор 4435, Ардхāсана — 4436,
  Сиддхāсана — 4437). Остальные шесть стихов (4375, 4428–4430, 4431, 4432–4434)
  остаются на странице раздела — в том же порядке и с той же нумерацией, что в
  издании, поэтому на странице раздела номера идут не подряд;
* сравнительная таблица части III — не таблица для `find_tables()`: ячейки
  переносятся по строкам, а порядок чтения перемешивает столбцы. `build_table()`
  собирает ячейки по столбцам (x ≈ 113 / 212 / 311 / 410), началом записи
  считает уход первого столбца вниз больше чем на строку, отбрасывает повтор
  шапки на второй странице и помечает занятые таблицей строки, чтобы они не
  попали в текст страницы ещё раз;
* приписка в скобках после стиха 4435 («текст и перевод совпадают со стихом
  4376») в карточку стиха не входит: `hoist_notes()` выносит её отдельным
  примечанием сразу за карточкой;
* заголовок части II служит и названием страницы раздела: `renderChapter()`
  больше не печатает первый подзаголовок второй раз под `<h1>`;
* `coverage()` печатает, сколько строк издания не попало в данные (сейчас 0 в
  обоих томах): каждая строка исходника проверяется дословно, включая таблицу.

### Раздел «Рукописи и издания»

У Ш́āрн̇гадхара-паддхати появилась страница `…/notes/` — та же схема адресов, что
у прочих разделов (`introduction`, `appendix`, `notes`). Это единственный раздел
сайта, которого нет в PDF: в `tools/sharngadhara_refs.py` собраны печатные издания
трактата (Петерсон 1888, перепечатки, Ауфрехт и Бётлингк), шесть рукописей
A–F из предисловия Петерсона, остальные списки по каталогу Ауфрехта, доступные
сканы и описания хранилищ — со ссылками. Первый блок страницы прямо говорит, что
раздел составлен для сайта и в подсчёт строк издания не входит; `coverage()` его
не проверяет, потому что проверять в PDF нечего.

Каждое издание и каждая копия снабжены ссылкой туда, где их видно и можно
скачать: скан 1888 года и перепечатка 1987 года на archive.org, том ZDMG 27 с
работой Ауфрехта, кембриджские списки в цифровой библиотеке, скан списка из
Сурата, записи NGMCP и IGNCA. Где скана нет (перепечатки Нирṇая-Сāгара,
брошюра Бётлингка), так и написано, а не подставлена похожая ссылка.

Что в этом разделе остаётся неразрешённым, сказано там же: сигла каталога не
развёрнуты до современных шифров, литеры E и F в перепечатке читаются плохо,
даты списков A и B — оценка Петерсона по бумаге, а Tod 32 датируют по-разному.

## Слово — из одного алфавита

Слово в русском тексте пишется либо целиком кириллицей (со знаками диакритики),
либо целиком латиницей (IAST): «Нирн̣айа», а не «Нирṇaya». Единственное
исключение — долгое «ā»: прекомпонованной кириллической «а с макроном» в Unicode
нет, поэтому карта `tools/translit.py` несёт макрон латинской буквой, и такая «ā»
внутри кириллического слова считается кириллицей.

Проверка и правка:

```
python3 tools/script_mix.py         # печатает находки
python3 tools/script_mix.py --fix   # переводит знаки в кириллицу
```

Скрипт проходит по `data/*.json`, `index.html` и `assets/app.js`. Латинская
буква с диакритикой внутри кириллического слова заменяется кириллической основой
с тем же знаком (`ṅ` → `н̇`, `ṭ` → `т̣`, `á` → `а́`). Слова с настоящей латиницей
(`ни-gad`) он не угадывает, а печатает — их правят вручную, и такие замены
записаны в `MANUAL`. Строки кода, имена файлов и сокращения вроде `OCR-чтение`
не проверяются.

## Диакритика в английском томе

Английский PDF печатает санскрит упрощённой латиницей английских книг
(`Shankara`, `Sureshvara`, `Manasollasa`, `Dakshinamurti-stotra`), а сайт
показывает IAST в обоих языках. Поэтому `tools/iast.py` переписывает
английский том перед выкладкой: `extract_manasollasa.py` вызывает
`iast_lib.fix_tree()` для `lang == "en"` — и для статьи, и для страниц асан.

Правила простые:

* меняются только те буквы, которых требует санскритская орфография
  (`sh` → `ś`/`ṣ`, `n` → `ṇ`, `t`/`d` → `ṭ`/`ḍ`, `a`/`i`/`u` → `ā`/`ī`/`ū`,
  `m` перед согласной → `ṃ`, `ch` → `c`); ни одно слово не добавляется и не
  переставляется — это карта целых слов (`MAP`), а не замена по буквам;
* адреса, имена файлов, шифры и `key`/`number`/`pdf` не трогаются совсем:
  `archive.org/details/…Sureshwaracharya…` остаётся как напечатано;
* санскритские названия мест пишутся с диакритикой (`Vārāṇasī`, `Śṛṅgeri`,
  `Kāñcī`, `Dvārakā`), а английские формы современных топонимов, названия
  учреждений и фамилии современных исследователей остаются как в источнике
  (`Mysore`, `Madras`, `Ramtek`, `Jammu`, `Aufrecht`, `Thrasher`, `Dasgupta`,
  `Kashi Hindu University`);
* два пункта §0, где справка сама описывала упрощённую запись, переписаны
  (`CONVENTIONS_EN`): теперь они описывают то, что сайт действительно делает.

Проверка: `python3 tools/iast.py` печатает контрольные строки; после правки
карты пересоберите JSON (`python3 extract_manasollasa.py ../data/manasollasa.json`
из `tools/`) — русский том не зависит от этой карты и остаётся дословным.
